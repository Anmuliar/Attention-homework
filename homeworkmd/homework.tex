\section{作业背景}
Attention 机制最初由 Google Brain 团队在 2017 年发表的论文《Attention Is All You Need》中提出\cite{vaswani2017attention}，旨在解决序列模型（如 RNN）在处理长序列时遇到的困难。该机制使模型能够动态关注输入序列的不同部分，从而提升机器翻译和文本生成等任务的性能。

Attention 使用查询（Query）、键（Key）和值（Value）进行计算：先计算 Query 和 Key 的点积并进行缩放，再对每一行应用 Softmax 得到权重，最后对 Value 加权求和。

\subsection{作业任务：大模型推理中的Attention算子}
\subsubsection{任务描述}
Attention 的计算公式为：

\begin{equation}
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right) V
\end{equation}
其中 $Q$、$K$、$V$ 为稠密矩阵或张量。Softmax 将每一行的分数转换为概率分布。对于向量 \( x = [x_1, \dots, x_n] \)，
\begin{equation}
\text{softmax}(x_i) = \frac{e^{x_i}}{\sum_{j=1}^n e^{x_j}}
\end{equation}

在大模型推理中，prefill 阶段和 decode 阶段的 Attention 存在差异：prefill 阶段处理完整输入序列，主要计算矩阵乘法（GEMM）；decode 阶段逐 token 生成，利用 KV cache（Key-Value cache，即预先保存的 Key 和 Value）避免重复计算历史 token，其中矩阵乘法退化为向量-矩阵乘法（GEMV）。在本作业的 decode 接口中，你不需要管理 KV cache；历史 cache 会由调用方生成并作为参数传入。在实际推理引擎中，cache 的分配、更新和布局也需要额外管理。

基本实现以及标准的输入输出接口可参考作业代码仓库的ops/base/impl.py部分。

本作业要求在单 GPU 节点上分别实现并优化 prefill 阶段和 decode 阶段的 Attention，占课程总成绩的 12\%。

\subsubsection{任务定义和接口}

\textbf{PREFILL}

Prefill 阶段输入完整的 Query、Key、Value：
\begin{itemize}[leftmargin=2.5em]
  \item $Q,K,V$ 的形状均为 $[B,H,L,D]$；
  \item 输出 $O$ 的形状为 $[B,H,L,D]$；
  \item 测试数据为 CUDA 上的连续 tensor，通常使用 \texttt{float16}；实现可以在
        float32 中累加以提高数值稳定性。
\end{itemize}

Python 适配层的函数名为：
\begin{lstlisting}[style=interface]
scaled_dot_product_attention_prefill(q, k, v, scale=None) -> o
\end{lstlisting}

\textbf{DECODE 和 KV Cache}

Decode 阶段只计算一个新 token。输入形状为：
\begin{itemize}[leftmargin=2.5em]
  \item $Q\in\mathbb{R}^{B\times H\times 1\times D}$；
  \item 新 token 的 $K,V\in\mathbb{R}^{B\times H\times 1\times D}$；
  \item 历史缓存 $K_{\rm past},V_{\rm past}\in\mathbb{R}^{B\times H\times T\times D}$；
  \item 输出 $O\in\mathbb{R}^{B\times H\times 1\times D}$。
\end{itemize}

逻辑上，decode 使用
\begin{equation}
  K_{\rm all}=\operatorname{cat}(K_{\rm past},K,\text{dim}=-2),\qquad
  V_{\rm all}=\operatorname{cat}(V_{\rm past},V,\text{dim}=-2),
\end{equation}
再计算 $\operatorname{softmax}(sQK_{\rm all}^{\mathsf T})V_{\rm all}$。作业接口把历史 cache 和新 token 分开传入。

函数名为：
\begin{lstlisting}[style=interface]
scaled_dot_product_attention_decode(
    q, k, v, past_k, past_v, scale=None
) -> o
\end{lstlisting}

\subsection{Online softmax}

为了说明 FlashAttention 一类方法为什么能够减少显存读写，先看直接实现
scaled dot-product attention 时会发生什么。假设 Query 的长度为 $L$，Key 和 Value
的长度为 $S$，head dimension 为 $D$。计算
\begin{equation}
  Z = QK^\mathsf{T}
\end{equation}
时，会得到一个形状为 $[L,S]$ 的分数矩阵 $Z$：第 $i$ 行第 $j$ 列表示第 $i$ 个
Query 与第 $j$ 个 Key 的缩放点积。接着对 $Z$ 的每一行做 Softmax，得到同样为
$[L,S]$ 的概率矩阵 $P$，最后计算 $O=PV$。因此，直接实现至少需要把 $Z$ 或 $P$
写入显存，并在后续计算中再次读出；当 $L$ 和 $S$ 较大时，这个中间矩阵的空间和
访存开销都很高。

Online softmax 的思路是把 Key 和 Value 按列切成 tile。每次只计算一小块分数
\(Z_{i,j}=Q_iK_j^\mathsf{T}\)，不把完整的 $L\times S$ 矩阵写回显存。为了让分块
计算与完整 Softmax 的结果一致，对每个 Query 行维护三个量：当前已经处理部分的
最大分数 $m$、经过缩放的指数和 $\ell$，以及已经归一化的部分输出 $o$。开始处理
一行时初始化为
\begin{equation}
  m=-\infty,\qquad \ell=0,\qquad o=0.
\end{equation}

对于一个新的 Key tile，先将越界位置的分数设为 $-\infty$，然后令
$m_{\rm tile}$ 为该 tile 每一行的最大值，并计算新的行最大值
$m_{\rm new}=\max(m_{\rm old},m_{\rm tile})$。在新的最大值下，旧 tile 和新 tile
的指数项分别需要乘上不同的缩放因子：
\begin{align}
  \alpha &= e^{m_{\rm old}-m_{\rm new}},
  &p_j &= e^{z_j-m_{\rm new}}.
\end{align}
其中 $z_j$ 是当前 tile 中某一行的分数。于是可以更新指数和与输出：
\begin{align}
  \ell_{\rm new} &= \alpha\ell_{\rm old}+\sum_j p_j,\\
  o_{\rm new} &=
  \frac{\alpha\ell_{\rm old}o_{\rm old}+\sum_j p_jv_j}
       {\ell_{\rm new}}.
\end{align}
完成所有 Key tile 后，$o$ 就是完整 Softmax 后的 Attention 输出。这个递推的关键
是始终减去当前行的最大值，因此不会直接计算很大的 $e^{z_j}$，数值上比先求完整
分数矩阵再做 Softmax 更稳定。实现时需要特别注意：如果你保存的是未归一化的
输出累加量，更新公式会略有不同；上面的公式假设 $o_{\rm old}$ 已经除以
旧的 $\ell_{\rm old}$。

Prefill 中通常同时处理多行 Query 和多个 Key tile；decode 中 Query 长度为 1，
但仍然可以沿着长度为 $T+1$ 的 KV cache 分块处理。这样 decode kernel 不需要先
拼接 $K_{\rm past}$ 和新 $K$，也不需要保存长度为 $T+1$ 的分数矩阵。Online softmax
只是可选的优化方向；直接保存分数矩阵的实现同样可以作为正确的起点，报告中应
说明两种实现的空间、访存和性能差异。

\subsection{Prefill 优化方向}

Prefill 的 $QK^\mathsf{T}$ 和 $PV$ 都具有比较高的计算密度。可以从以下问题开始
分析：
\begin{itemize}[leftmargin=2.5em]
  \item 如何让 Q、K、V 的读取合并，并让重复使用的数据停留在 SRAM 或寄存器中；
  \item $BLOCK\_SIZE\_M$、$BLOCK\_SIZE\_N$、warp 数和 pipeline stages 如何影响
        occupancy、寄存器压力和内存管理；
  \item 是否值得避免 $L\times S$ 中间张量，以及这样做对寄存器和访存的影响；
  \item 如何处理 $L$、$D$ 不是 tile 大小整数倍的边界。
\end{itemize}

\subsection{Decode 优化方向}

Decode 的 Query 长度固定为 1，计算常常受 KV cache 读取和并行度限制。可以分析：
\begin{itemize}[leftmargin=2.5em]
  \item 一个 program 是否能隐藏 KV cache 的访存延迟；
  \item 是否需要沿 Key 长度切分，再对多个 partial result 做归约；
  \item 如何让相邻线程访问连续的 head dimension，并控制中间状态的大小；
  \item $T$ 较短和较长时是否应采用不同的配置。
\end{itemize}

这些只是分析入口，不要求所有人使用同一种算法。报告应结合实际测量说明你的
选择，不需要为了使用某个术语而强行改写算法。
